# uni-app 页面开发

## 先读与输入

以下路径相对项目根目录解析。先读 `AGENTS.md`、`docs/engineering/architecture.md`、`docs/engineering/development.md`、`docs/engineering/verification.md`、`docs/design/ui-guidelines.md` 和 `docs/security/child-safety.md`。涉及内容展示时读 `docs/content/card-standard.md`。

接收：页面目标、用户操作、明确验收标准、目标端、设计依据及获准数据。先发现并阅读现有页面注册、组件、样式变量、类型和依赖配置，再决定修改位置；复用既有架构，不凭模板另起一套。

## 执行步骤

1. 划清当前初始化范围与新需求。现有五主题选择查看三个篇章是导航演示，不代表课程、打卡、账户、收藏或海报业务已实现；不得填入虚构进度、儿童记录或假接口制造完成感。
2. 按现有 uni-app Vue3、TypeScript 和 CLI 约定实现。优先 `view`、`text`、`button`、`image` 等原生跨端组件及 `uni.*` API；不直接搬入仅浏览器可用的 DOM、`window` 或 `document` 方案。
3. 将平台差异集中在必要边界，按仓库约定采用条件编译；微信能力不可用时明确限制，不以H5成功冒充小程序成功。沿用官方兼容版本，不单独升级某个 DCloud 包，不默认添加依赖或UI框架。
4. 使用已有设计变量，保留文字对比度、足够点击区域和清晰焦点；信息不能仅靠颜色区分。处理窄屏、系统字体放大、安全区及长中文换行，不强制裁掉内容实现“一屏”。
5. 仅实现需求所需的状态和交互，按钮必须有真实作用；没有业务能力时不要放置可点击却无效果的入口。不得引入在线AI、后端、支付、遥测、真实儿童资料或持久化，除非任务另行明确授权并完成相应设计。
6. 更新受影响的调用位置和相关现有文档，不建兼容空壳。按验证规范运行类型检查、受影响平台构建与实际交互检查；多人或多代理协作时约定一名集成负责人统一执行，独立执行任务时自行完成验证。不重复他人已报告的错误，也不将未执行检查标为通过。

## 结构化交付

交付：

- **变更清单**：文件、改动目的、复用的现有组件或样式、页面注册变更。
- **行为说明**：输入与操作、真实输出、目标端差异、范围外能力。
- **数据边界**：数据来源、是否涉及网络／权限／持久化；禁止把示意内容描述为真实业务数据。
- **验证交接**：验收步骤、建议命令、微信开发者工具人工检查点；分别记录已执行、未执行、阻塞项。命令以当前 `package.json` 和验证文档为准，不虚构测试套件或测试结果。

## 质检与人工闸门

核对跨端组件、路由注册、类型与资源引用、无新增秘密凭据、无假状态和无效交互、无平台API无保护调用；初始化阶段不存在的业务测试套件必须如实说明。

发布前由主代理或维护者统一完成类型检查、H5与微信构建及实际交互检查；视觉审阅由人工确认。课程或儿童信息展示还须通过内容与隐私闸门，不能用构建成功替代内容批准。
